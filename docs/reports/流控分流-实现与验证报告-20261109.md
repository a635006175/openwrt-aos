## 一、需求与结论

用户要求：新增一级菜单「流控分流」，内容为参考图所示的爱快式结构——分流设置（多线负载/协议分流/端口分流/域名分流/上下行分离）、智能流控、终端限速；并明确要求**优先复用已有插件或开源实现**。

结论：经逐项核查，本机环境下没有任何现成插件能直接承担这些功能（详见 `.stage/flow-research.md`），因此采用「**能力替代 + 上游机制复用 + 复用本仓库既有工程模式**」的方式自研，并在页面上如实标注降级边界。

主要复用来源：

| 复用对象 | 复用内容 |
| --- | --- |
| mwan3 / pbr / mihomo | fwmark → `ip rule` → 独立路由表的分流骨架 |
| nft-qos / WanBlendr 思路 | nftables `limit`/`quota` 丢包式限速、连接级负载均衡 |
| `console-portmap.uc` | 模型校验 + `nft -c` 预检 + 原子替换 + `/etc/console-backup` 备份 |
| `console-security.uc` | `pending.json`（boot_id + 单调 uptime）→ 120 秒确认窗口 → 超时回滚 |
| 既有 rpcd ucode + ACL 分离 | read/write 分权、异常统一转中文 `{error}` |
| 已装组件 | DHCP 租约、`/etc/config/dhcp` 静态保留、`/proc/net/arp`、`console_meter` 计数作数据源 |

## 三、开发过程中发现并修复的缺陷

以下问题都是**在实机复现后修复**的，不是靠读代码推测。按发现顺序：

| # | 问题 | 后果 | 修复 |
| --- | --- | --- | --- |
| 1 | `weightedPool()` 按权重展开后被 `seen` 去重折叠回每线一次 | **权重完全失效**，多线负载退化成均分 | 改为 `weightVmap()` 按权重生成区间 |
| 2 | `numgen random` 逐包求值，且还原条件是 `ct state established,related` | SYN 重传期间连接仍是 `new`，**同一 TCP 连接握手前跨线路抖动**，对端看到不同源 IP，握手失败 | 还原判据改为 `ct mark & 0xffff0000 == 0x46460000`（避开 mihomo 的 `0x434d`）；负载选择器改 `jhash` 五元组 |
| 3 | UI 允许绑定 MAC，`flow-model.uc` 也校验保存，但引擎只按 IP 生成规则 | **「看起来有、实际没有」**，用户以为已绑定 | 上行加 `ether saddr`、下行加 `ether daddr` |
| 4 | `flow-model.uc` 的 `lined()` 用了 `(value||'').trim()`，**ucode 字符串没有 `.trim()` 方法** | 用户只要填 MAC 就抛异常，**整页保存失败** | 改 `trim(value \|\| '')` |
| 5 | rpcd ucode 方法内同步调 `luci-rpc.getHostHints`（该对象由 rpcd 自己的 luci.so 提供） | **rpcd 等自己，恒定卡满 30 秒 ubus 超时**，7 个页面全部打不开 | 删除该调用，`devices()` 改本地文件三源合并（租约 + 静态保留 + ARP） |
| 6 | `flow.js` CSS 注入用 `console-security-css` 作外条件 | 先访问过安全页时 **flow.css 永不加载**，样式错乱 | 两者各自检查自己的 id（flow-ui 自查修复） |
| 7 | `flow-load.js` 把 `flow.table()` 返回的 `{body,element}` 当节点塞进 children | 页面出现字面量 **`[object Object]`** | 先建表再 push element；同时修 4 处 `E(..., 单个DOM元素)` 写法 |
| 8 | `rpc.declare({params:['config']})` 调用时又包了一层 `{config}` | 实际发出 `{"config":{"config":{...}}}`，**后端拿到空配置，保存永远丢数据** | 改为 `callCheck(config)` / `callApply(config)` / `flow.resolve(config)` |

第 5、7、8 项只有在「真实浏览器 + 真实 rpcd」下才会暴露：裸 ucode 测 `state()` 是 0ms 正常的，静态检查也发现不了 `[object Object]` 和双层包裹。

## 五、遗留问题与建议

1. **限速无整形**：内核未编译 `sch_htb`/`sch_cake`/`kmod-ifb`，只能丢包限速。若用户要求低延迟、不重传的整形能力，需重编内核并引入 tc，属于另一轮工作且违反当前「不重编内核」前提。页面已常驻提示。
2. **`failover` 模式粒度**：只用第一条可用线路，掉线后由守护进程（60 秒周期）顺延，最坏 60 秒。若要秒级切换需加主动 ICMP 探测，但会误判屏蔽 ICMP 的线路，权衡后未做。
3. **域名分流只解析 A 记录**，IPv6 域名不参与分流；解析依赖本机 DNS，DNS 不可用时保留旧地址并提示。
4. **智能流控依赖终端列表**：`console-security` 采集器未运行时，只有 DHCP 租约内设备能被限速。
5. **未编译进镜像**：按用户要求开发期不重编。固件若要包含本功能，需在构建机 `make menuconfig` 确认 `luci-app-console` 选中并重编 payload/ISO。
6. **rpcd 模块缓存**：升级 `flow-*.uc` 后必须 `/etc/init.d/rpcd restart`，否则跑旧 inode（与 `console-security` 同一坑）。部署脚本已含该步骤，init.d 内故意不重启以避免 ubus 竞态。
7. **多线负载在单 WAN 环境无法真正验证分流效果**：本机只有 1 个真实外网口（eth1），测试中用同一接口建了两条线路来验证 mark/rule/route 链路，**未能在两条真实不同出口上验证实际带宽分配比例**。这是本轮验证的客观缺口，需有第二路外网时补测。

```
  console-mihomo (no such package): required by: luci-app-console-0.3.0-r1[console-mihomo]
```

原因：设备上 `console-mihomo` 的**文件是通过 SSH 手工部署的，从未以 apk 包形式安装过**，
`apk info -W /usr/share/ucode/console/mihomo.uc` 返回 `Could not find owner package`。
另外设备 `/etc/apk/repositories` 为空（无上游仓库），所以无法解析该依赖。

解决：编译机已有 `console-mihomo-1.19.33-r1.apk`，先装它建立正式包记录，再装主包：

```
apk add --allow-untrusted --force-non-repository /tmp/console-mihomo.apk
  → console-mihomo-1.19.33-r1 [installed]

apk add --allow-untrusted --force-non-repository /tmp/luci-app-console.apk
  → Installing ucode-mod-math（自动补齐缺失依赖）
  → Upgrading luci-app-console (0.1.0-r1 -> 0.3.0-r1)
  → post-upgrade 执行成功
```

安装前记录：设备上 `luci-app-console` 原本是 **0.1.0-r1，且包记录只覆盖 6 个文件**（极早期版本），
其余大量文件都是历史手工部署、无包管理记录。本次安装后，**19 个 flow 相关文件全部纳入包记录**，
可通过 `apk del` 正常卸载。
